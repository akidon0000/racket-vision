# improve-vision-accuracy

映像の解析の精度を、サンプル動画で測って直す手順。コードは Swift パッケージ racket-vision（このスキルと同じリポジトリ）にある。使う側のアプリのリポジトリで作業していても、測るのはこのパッケージで行う。対象ごとの測り方は `references/` にある。

| 対象 | 状態 | 読むもの |
| --- | --- | --- |
| コートの検出（`CourtFit`） | 実装済み。測る仕組みもある | [references/court.md](references/court.md) |
| 骨格分析（選手の姿勢） | 未実装。測る仕組みもまだ無い | [references/pose.md](references/pose.md) |

対象を決めたら、その参照ファイルを先に読む。対象が増えたら、`references/<対象>.md` を足し、上の表に 1 行足す。

## なぜこの手順か

精度の改善で一番起きやすい失敗は、数字だけを見て「良くなった」と思い込むこと。実際に、次の 3 つが起きた。

- 「検出率」（何か返したフレームの割合）が 84% あったのに、中身の大半は観客席への誤りだった。誤りを弾いたら 10% に下がり、そのほうが正しかった。
- 1 本の動画に合わせて閾値を変えたら、別の動画で正しく当たっていたフレームが消えた。
- シミュレーターで枠が古いまま残って見えたが、原因は検出ではなく Debug ビルドの遅さだった。

だから、測る・見る・比べるを毎回セットで行う。

## 手順

### 1. 準備

- サンプル動画（`.mp4`）は、git に入れずに手元のフォルダに置き、そのフォルダを環境変数 `COURT_DEMO_DIR` で渡す。置き場所が分からなければユーザーに聞く。動画が足されていないか、ファイルの一覧と大きさ（縦長か横長か）を最初に確かめる。新しい種類の動画は、それまでの前提を崩しやすい。
- 測るのは Release ビルドで行う（`xcrun swift test -c release -Xswiftc -enable-testing ...`）。Debug は画素を回す計算が数十倍遅く、全動画を測ると何分もかかる。`swift test` は `xcrun` を付けて呼ぶ（付けないと `-target-arch-variant` で失敗する）。
- 出力（JSON、画像、表）は、セッションの一時フォルダ（scratchpad）に置く。残す結果だけを、最後に記録の場所へ写す。
- 比べ合わせの道具は、このスキルの `scripts/` にある。`contact_sheet.swift` は、一度 `xcrun swiftc -O <スキルのフォルダ>/scripts/contact_sheet.swift -o <一時フォルダ>/contact_sheet` でビルドしてから使う。

### 2. 直す前を測る

対象の参照ファイルにある「書き出し」と「採点」を実行し、直す前の結果を残す。この結果が、あとで回帰（直したせいで悪くなったところ）を見つける基準になる。

### 3. 目で見る

数字の前に、結果を描いた画像を並べて見る（`contact_sheet`）。見るのは次の 3 点。

- 当たっているか（枠や点が、本物に重なっているか）
- 外れを出していないか（無いはずの場所に出していないか）
- 出すべきなのに出していないフレームはどれか

見て分かった「外れ」と「見逃し」を、動画名と秒で書き留める。これが次の仮説の材料になる。

### 4. 原因を突き止める

落ちているフレームを数枚選び、途中の段階を画像で確かめて、どの段で落ちているかを決める（段の分け方は参照ファイルにある）。原因が分かる前に閾値を動かさない。閾値を動かして通るようになっても、なぜ通ったかが分からなければ、別の動画で壊れる。

### 5. 直す

- 一度に 1 つだけ直す。2 つ同時に直すと、どちらが効いたか分からない。
- 特定の動画だけに効く直し方（その動画の色や位置に合わせた値）は避ける。直す理由を「この種類の映像では、こういう理由でこう落ちる」と一般化して書けるものだけを入れる。
- 値は、映像の大きさに比例させるなど、撮り方が変わっても意味が保たれる形にする。

### 6. 測り直して比べる

全動画で測り直し、`scripts/compare_exports.py diff` で直す前と比べる。変わったフレームは全部、目で確かめる。

- 狙った動画で良くなったか
- ほかの動画で、正しかったフレームが消えたり動いたりしていないか

悪くなったフレームがあれば、5 に戻る。直す前より悪くなったまま終えない。

### 7. 確かめる

- パッケージの直下で、単体テスト（`xcrun swift test`）、整形（`swiftformat --lint .`）、Lint（`swiftlint lint --strict`）を通す。
- 画面で確かめるときは、パッケージを取り込んだアプリをシミュレーターで動かし、サンプル動画を流す。アプリの側で、この検出を Release 相当の最適化でビルドしないと、1 フレームに数秒かかって枠が遅れて見える。`xcodebuild` は `ARCHS=arm64 ONLY_ACTIVE_ARCH=YES` を付けないと、x86_64 向けのビルドでパッケージと合わずに失敗することがある。

### 8. 記録する

結果は、パッケージの `docs/accuracy/<対象>.md`（例: `docs/accuracy/court.md`）に追記する。書くのは次のとおり。

- 何を直したか、なぜか（どの種類の映像で、どの段で落ちていたか）
- 動画ごとの、直す前と後の数（何を数えたかも書く。「何か返した数」と「正しく当たった数」は違う）
- 目で確かめた結果と、確かめていないこと
- 残っている問題と、次の手

## 報告の形

ユーザーへの報告は、次の順で書く。

1. 一文目で結論（どの動画で、どれだけ良くなったか。良くならなかったものも）
2. 直したこと（理由つき、1 行ずつ）
3. 動画ごとの前と後の表
4. 残っている問題
5. 確かめたこと・確かめていないこと（テスト、Lint、シミュレーター）

数字には、その数字が何を数えたものかを必ず添える。正解を自分の結果から作ったとき（目で確かめた結果を基準にしたとき）は、その旨と、基準から外したフレームを書く。
