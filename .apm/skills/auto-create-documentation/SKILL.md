# 変更の記録

構成、運用手順、スキル、ビルドやテストの手順、モジュールの境界を変える変更で使う。目的は、変更後のパスやコマンドだけでなく、後も効く判断と、その再評価の条件を残すこと。

## 記録先の選び方

| 何が変わったか | 記録先 |
|---|---|
| 採用・不採用、モジュールの境界、外部依存、守るべき規則、再評価の条件を伴う割り切り | ADR（[write-adr](../write-adr/SKILL.md)） |
| 作業者が辿るパス、コマンド、ワークフロー | 該当する wiki-* スキル（[wiki-repo](../wiki-repo/SKILL.md) の「wiki-* に残す変更」）。精度の改善と動画の切り出しの手順は、それぞれ [improve-vision-accuracy](../improve-vision-accuracy/SKILL.md)、[clip-play-videos](../clip-play-videos/SKILL.md) |
| 精度の計測の結果、外れ方、確かめた条件 | `Docs/accuracy/<対象>.md`（improve-vision-accuracy の「記録する」） |
| 判断に迷うもの、確かめられない事実 | `wiki-repo` の「要確認」。ADR にはしない |
| 意味も運用も変えない局所的な修正、機械的な整形 | 記録しない |

`CLAUDE.md` は、エージェントが最初に読む入口と、毎回調べ直していた短いメモだけを置く。手順の本体は wiki-* やスキルに書き、`CLAUDE.md` からはその名前を指す。

## 作業

1. まず [Docs/adr/README.md](../../../Docs/adr/README.md) と wiki-* スキルを読み、既存の決定と手順を確かめる。
2. 変更で確定した判断を特定する。確定していなければ、ADR には書かない。
3. 判断があれば、`write-adr` で ADR を書き、一覧を更新する。既存の決定を覆すときは、旧い ADR の `status` と参照を更新する。
4. 手順が変わったら、該当する wiki-* やスキルの節を直す（[write-wiki](../write-wiki/SKILL.md)）。
5. 迷ったものは、`wiki-repo` の「要確認」の節に 1 件 1 行で書く。例: `- <項目>: <何が分からないか>`
6. 旧いパスや旧いコマンドが残っていないか検索する（`rg <旧いパス>`）。リンク先が存在するか確かめる。
7. スキルを直したら、`apm install` で展開し直す（`wiki-repo` の「スキルを足す・変える」）。
8. 結果を報告する。更新した記録を挙げる。記録しないと判断したときは、理由を一文で書く。

## 制約

- 会話に出ただけの案を、確定した決定として書かない。
- コードから分かる細かい情報や、変更履歴そのものを ADR に複製しない。
- 旧い ADR の内容を消さない。覆すときは後の ADR で置き換える。
- ドキュメントを更新するだけの理由で、ビルドや配布の操作をしない。
- ユーザーに確認したい判断は、この skill では決めない。「要確認」に書き、最後の報告で伝える。
