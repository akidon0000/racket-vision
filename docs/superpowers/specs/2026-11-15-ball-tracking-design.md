# ボール追跡（`BallTracking`）の設計

- 読み手: `BallTracking` を実装する人（エージェントを含む）と、実装の前に中身を確かめる人
- 目的: 実装に入る前に、何を作り、何を作らず、どう確かめるかを決める

## 位置づけ

映像の解析を 4 つのライブラリに分ける。今回作るのは 1 つ目の `BallTracking` だけで、完成したらサンプル動画で評価する。残りの 3 つは、評価のあとに、それぞれ同じ形の文書を書いてから作る。

| 順 | ライブラリ | 出すもの | 依存 | 今回 |
| --- | --- | --- | --- | --- |
| 1 | `BallTracking` | フレームごとの球の位置と、ラリーごとの軌跡 | なし | 作る |
| 2 | `LineCalling` | バウンドごとのイン/アウト | `BallTracking`、`CourtFit` | 作らない |
| 3 | `PlayerPose` | 選手 2 人または 4 人の関節 | `CourtFit` | 作らない |
| 4 | `PlayerHeatmap` | 選手のコート上の座標と、ヒートマップ | `PlayerPose`、`CourtFit` | 作らない |

## 作るもの

連続するフレームを順に渡すと、フレームごとに球の位置を返すライブラリ。返した位置をラリーごとの軌跡にためる型も持つ。軌跡は点で表示し、ラリーが変わるたびに色を変え、ラリーが終わったら消す。

表示する場所は 2 つある。

| 場所 | 中身 | 使いみち |
| --- | --- | --- |
| `DemoApp` の再生画面 | 動画を流しながら、球の軌跡の点を重ねる | 動きを見る |
| 評価用の書き出し | サンプル動画の全フレームを流し、点を描いた動画（mp4）と、0.5 秒ごとの画像を書き出す | コマ送りで当たり外れを確かめる |

### 決めたこと

| 項目 | 決定 |
| --- | --- |
| 方式 | 画像処理で書く。動いていて、球の色をしていて、球の大きさの塊を拾い、軌跡がつながるものを球とする |
| 学習済みモデル | 使わない |
| 入力 | 32BGRA の `CVPixelBuffer` と、そのフレームの時刻（秒）。向きは上向きだけを受ける |
| 座標 | 映像の大きさに対する 0〜1 の正規化座標、左下が原点（`DetectedQuad` と同じ） |
| 状態 | 検出器が前のフレームと追跡中の軌跡を覚える。動画 1 本（または撮影 1 回）ごとに作り直すか `reset()` を呼ぶ |
| 方式の差し替え | `BallDetector` の protocol で、同じ入出力にする |
| 球の数 | 1 個。同時に複数の球は追わない |
| ラリー | 1 回打ってから、相手が打ち返すまでを 1 つのラリーとする。球の速さ（向きを含む）が短い時間で急に変わり、打った位置のほうへ戻ってきたら、打ち返されたとみる。球が 2 秒見えないか、場面が切り替わったときも、ラリーの終わりとする（2026-11-15 に「球を追えているひと続き」から変えた） |
| 軌跡の色 | ラリーの番号で、色の並び（6 色）から順に選ぶ。色の並びはライブラリが持ち、`DemoApp` と評価用の書き出しで同じ色にする |
| 最適化 | `CourtFit` と同じく、Debug でも最適化してビルドする |

### API

```swift
import BallTracking

let detector = MotionColorBallDetector()
var rally = BallRallyTrajectory()

// フレームが届くたびに呼ぶ（時刻は秒。映像の先頭からでも、撮影の開始からでもよい）。
let outcome = detector.detect(in: pixelBuffer, at: seconds)
rally.append(outcome)

outcome.ball?.center                              // 球の中心（正規化座標、左下が原点）。見つからなければ ball は nil
rally.samples                                     // 今のラリーの軌跡の点。ラリーが終わると空になる
BallRallyPalette.color(forRally: rally.rallyIndex) // 今のラリーの色（赤・緑・青、0〜1）
```

| 型 | 中身 |
| --- | --- |
| `BallObservation` | 球 1 個。中心（正規化座標）、半径（映像の幅に対する割合）、確からしさ（0〜1） |
| `BallFrameOutcome` | 1 フレームの結果。方式、時刻、球（無ければ nil）、候補の一覧（確認用）、場面が切り替わったか、処理時間（ms）、映像の大きさ |
| `BallDetectionMethod` | 方式の名前（`rawValue` と表示名）。使う側が自前の方式を足せるよう、`CourtDetectionMethod` と同じく値で表す |
| `BallDetector` | protocol。`method`、`detect(in:at:)`、`reset()` |
| `MotionColorBallDetector` | 最初の方式（下の「仕組み」）。設定は `BallColor`（球の色。既定は黄緑）と、大きさの範囲 |
| `BallSample` | 軌跡の 1 点。時刻、中心、半径、確からしさ |
| `BallRallyTrajectory` | 今のラリーの `BallSample` の並びと、ラリーの番号。`append(_:)` で足す。ラリーが終わると、点を消して番号を 1 つ進める |
| `BallRallyPalette` | ラリーの番号から色を返す |

### 仕組み（`MotionColorBallDetector`）

| 段 | 処理 | 落とすもの |
| --- | --- | --- |
| 1. 場面の切り替わり | 1 つ前のフレームから動いた画素が画面の 2 割を超えるとき、そのフレームは球を出さず、追跡を捨てる | カメラの切り替え、大きな手ぶれ |
| 2. 動きと色 | 今のフレームが、1 つ前とも 2 つ前とも違い、球の色（既定は黄緑: 色相 55〜105 度で鮮やか。明るい画素は、薄くても通す。コートの矩形が渡されているあいだは、薄い緑まで通す）の画素を種にする | 止まっている黄色（ロゴ、線、置いてある球）、選手の体や影、ラケット |
| 3. 塊 | 種から、球の色でつながる画素をたどって塊にする（遅い球は、動いた画素が縁だけになるため）。大きさ（直径が映像の幅の 0.2〜2%）と細長さ（3 対 1 まで。ぶれて伸びた球を通す）で絞る。たどった塊が大きすぎたら捨てる | 黄色い服、靴、観客 |
| 4. 範囲 | コートの矩形が渡されていれば、矩形と、矩形を上へ持ち上げた形（空中の球のため）を囲む範囲の外の候補を捨てる | 観客、看板、隣のコート |
| 5. 追跡 | 追跡中なら、前の位置と速さから次の位置を見込み、近い候補を選ぶ。無ければ、見込みの位置の近くだけを緩い条件（薄い色、小さな動き）で探し直す。それも無ければ、向きが変わったとみて、少し広い範囲の候補へ移る。追跡が無ければ、候補から仮の軌跡を始め、続けてつながって球の速さで動いたものを球として出し始める | 1 フレームだけ光った誤り、同じ場所でちらつく黄色、ゆっくり動くもの |
| 6. 見失い | 候補が無い時間が続いたら追跡を捨てる（球が選手やネットに隠れた、画面から出た）。見失っているあいだに、別の仮の軌跡が球と言えるようになったら、そちらへ移る | — |

段 5 と 6 の「続けて」「続いたら」は、フレームの数ではなく秒で決める。サンプル動画は毎秒 30 コマと 60 コマが混じっているためである。最初の値は、球として出し始めるまでが 0.08 秒、見失ってから追跡を捨てるまでが 0.3 秒。サンプル動画で測って直し、直した値と理由を `docs/accuracy/ball.md` に残す。大きさの範囲は映像の幅に対する割合で持つ。切り出したフレームを拡大して目で測った球の直径は、1min-04 で約 18px、1min-01 で約 8px（どちらも幅 1920px）で、0.2〜2% の範囲に入る。

## 作らないもの

- 球の高さ、3 次元の位置、速さ（m/s）、回転
- イン/アウトの判定とバウンドの検出（`LineCalling` で作る）
- 学習済みモデルを使う方式（方式を足せる形にはしておく）
- 複数の球の同時追跡
- `DemoApp` のカメラの画面（`CameraDetection`）での表示
- 上向き以外の向き（回した映像）
- 球の位置の正解づけと、正解との採点（評価のときに、要るかどうかを決める）

## 確かめ方

| 確かめるもの | やり方 |
| --- | --- |
| 計算が正しい | 合成したフレーム（青い背景に、動く黄緑の円、止まった黄色の四角、動く大きな塊）を渡す単体テスト。球の位置が 1.5px 以内で返ること、止まった黄色を出さないこと、場面の切り替わりで追跡を捨てること、ラリーが終わると点が消えて番号が進むことを見る |
| サンプル動画で当たる | `COURT_DEMO_DIR` を指定したときだけ動くテストで、動画を先頭から全フレーム流す。0.5 秒ごとの画像（軌跡の点つき）、フレームごとの球の位置の JSON、動画ごとの集計（球を出したフレームの割合、ラリーの数、平均処理時間）を書き出す。指定すれば、点を描いた動画（mp4）も書き出す。画像を並べて目で見る |
| 速さ | Release ビルドで、1080p の 1 フレームあたりの平均処理時間を測る。目標は 20ms 以下（この Mac。実機では未計測のままになる） |
| `DemoApp` | シミュレーターで動画を流し、球に点が付くこと、ラリーが終わると点が消えることを画面で見る |

結果は `docs/accuracy/ball.md` に、動画ごとの数と、目で見て分かった外れ・見逃しを書く。測る手順は `skills/improve-vision-accuracy/references/ball.md` に足す。

## 分かっている限界

- 球が小さい映像（1min-01 は直径約 8px）では、ネットの網や観客に紛れて取りこぼす。
- 手持ちで揺れる映像（縦長のショート動画）では、画面全体が動くので、段 1 が働いて球を出さないフレームが増える。ラリーの途中でも、そこで軌跡が消える。
- 打ち返しは球の速さの変化で決めるので、打った前後で球を見失うと、色が変わるのが遅れるか、変わらない。急な角度で落ちてバウンドした球を、打ち返しと取り違えることがある。球が見えなくなってから点が消えるまでに 2 秒かかる。
- 黄緑でない球（オレンジ、白など）は、`BallColor` を変えないと拾わない。サンプル動画では、09 がオレンジの球、10 が白っぽく写る球で、既定の色では拾えない。
- 球と同じ色で同じ大きさの動くもの（黄緑の靴の先など）を、球と取り違えることがある。
- `DemoApp` は、検出が間に合わないフレームを飛ばす。シミュレーターでは、評価用の書き出しより取りこぼしが増える見込み。

## 根拠

- 学習済みモデルを使わない理由: ピックルボールの球の学習済みモデルも学習データも手元に無い。パッケージは外部への依存が無く、テストはホストの macOS でそのまま動く。この形を崩さずに作れて、サンプル動画で測れるのは画像処理の方式だけである。
- 動きと色を両方使う理由: サンプル動画のコートには、止まった黄色（ロゴや線）と、動く黄色でないもの（選手）が両方ある。片方だけでは候補が絞れない。
- 入出力を `CourtFit` に合わせる理由: 使う側のアプリは、同じフレームをコートの検出と球の検出の両方に渡す。座標の向きがそろっていれば、`LineCalling` で変換を挟まずに済む。
- ラリーの区切りをライブラリに置く理由: 「どこでラリーが終わったか」は、表示（色替えと消去）だけでなく、あとで作る `LineCalling` も使う。表示の側に書くと、`DemoApp` と評価用の書き出しで区切りが食い違う。
- 評価用に動画も書き出す理由: `DemoApp` は検出が間に合わないフレームを飛ばすので、当たり外れを数えるのには向かない。全フレームを処理した結果をコマ送りで見られるものが要る。
- `VideoTestSupport` を分ける理由: 4 つのライブラリのテストが、どれも動画を順に読んで画像を書き出す。テストのターゲットごとに写すと 4 か所で食い違う。
